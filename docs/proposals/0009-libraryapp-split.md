In plain language: the main window class, `LibraryApp`, is the last big un-split piece of the app — one class with 74 methods that does the window, the table, the loading and syncing, and the dialogs. This proposal splits it into four standalone components, following the same pattern as the Course Builder, Advanced Search, and Distribution Panel: a Data Paths dialog, a background data engine (loading and syncing), a filter pipeline, and the table. Nothing the user sees changes. The filter is its own component because its inputs form a disjoint group from the table's, and because the three-component design has a constructor cycle between the table and the Distribution Panel that the split removes (§7, Q1).

## 1. Background and Goal

The split sequence is nearly complete. Course Builder (proposal 0001), Advanced Search (0004), the Distribution Panel (0005), and the settings/snapshot stores (0008) are all standalone components with constructor contracts a reader can see in one place. What remains is the shell they hang off: `LibraryApp` itself. It is the largest single concentration left in the codebase, and the only class that still mixes window management, data loading, and display logic in one place.

That is why this proposal exists before any code moves. The seams here are the most coupled in the app — the table, the filter, and the loader all read and write the same state — so the boundary decisions need to be made up front, not discovered mid-move. Nothing about the app's appearance or behaviour changes; the goal is four components owning their areas end to end, with constructor contracts a reader can see in one place, as with the four splits before this one. "Done" means `LibraryApp` is a thin shell — it builds the window, creates the stores and the components, wires them together, and owns the settings save — and each component is understandable from its own one-sentence description without holding the rest of the file in mind.

This change creates four new component boundaries and four new constructor contracts, so it needs a proposal. It does not persist a new settings key or file format.

## 3. The Decision: Four Components, Staged

### Option A (recommended): four standalone components, one per cluster

Four new modules, each owning one cluster end to end, mirroring the existing components: the dialog owns its widgets and its note logic; the loader owns its workers, its queue, and its progress/status reporting; the filter owns the five variables, the search box, and the rows it filters; the table owns the Treeview, its columns and sorting, and selection. The app keeps the shell and coordinates: it creates the stores and the components, passes each its constructor inputs, and wires the callbacks. Each component's constructor contract is stated in §4, and the one-sentence description each must pass is given there too.

The two boundary decisions (Q1, Q2) were the closest calls in the first draft and are recorded in §7 with the panel's positions and the owner's decision: the filter splits out (Claude's recommendation, adopted), and the handlers' engine half moves into the loader (Claude's recommendation, adopted).

### Option B: extract the pure logic only, keep the window in the app

Move `_invalid_paths_note` and any other Tk-free helpers to `library_data.py` (the §6 extraction step does this for the note) and stop there. Worth doing on its own merits — this proposal includes it as a step — but as the whole answer it leaves 55 methods and 1,050 lines inside `LibraryApp`; the split's point is not achieved.

### Option C: a mixin class for `LibraryApp`

Rejected for the same reason as in proposals 0001, 0004, and 0005: it hides the boundary instead of stating it, against the owner's standing guideline of legibility for a human reviewer.

## 4. Recommended Design in Detail (Option A)

**DataPathsDialog** (`data_paths_dialog.py`). One sentence: the one dialog where the two library paths are edited, which opens at startup when there is nothing to show and re-opens from the File menu. Its constructor inputs, stated per the proposal 0001 safeguard:
1. `parent` — the root window, for the Toplevel.
2. `cache_var`, `stats_var` — the two path variables, shared objects; the dialog edits them, the app and the loader read them.
3. `load_callback` — a zero-argument callable, invoked when the user presses Load (today's `load_data`, which takes no arguments).
4. `save_settings` — callable, invoked when a path is chosen (today `choose_cache`/`choose_stats` save).
5. `button_factory`, `entry_factory` — the themed widget factories, the precedent from the other components. (`combo_factory` is not listed: the dialog has no combobox — `_path_row` uses `_entry` and `_button` only.)
6. `dpi_scale` — the display scale factor, for the path rows and the note line.
7. `paths_match_loaded` — a zero-argument callable returning whether the dialog's paths match the loaded snapshot's sources (today's `_current_paths_match_loaded`), so the dialog can show the "differs from loaded" note.

The three note constants move into the dialog module (they are dialog text). `_invalid_paths_note` moves to `library_data.py` in §6's extraction step — it is stateless — and the dialog imports it. The dialog exposes `open()`, `set_note(text)`, `maybe_show_first_run(snapshot_loaded, had_saved_paths)`, and `paths_changed()`. The first-run check takes its two facts as arguments — whether a snapshot is loaded and whether saved settings contained path keys — which the dialog cannot derive from its inputs (the `paths_match_loaded` callable returns True both when nothing is loaded and when the paths match). `paths_changed()` computes the 'paths differ' note itself (it has `paths_match_loaded`), so `_source_paths_changed` calls it instead of the loader importing the dialog's note constant. The dialog does not reach back into the app: it never touches the table, the stores, or the status line. The dialog and the loader need each other (the dialog's `load_callback` and `paths_match_loaded` are the loader's methods; the loader needs the dialog's `open`, `set_note`, and `maybe_show_first_run`) — the construction order that breaks the cycle is stated in the App side paragraph.

**LibraryLoader** (`library_loader.py`). One sentence: the background data engine — it loads the library (scan or snapshot), syncs scores, and reports progress and status, all off the main thread. Its constructor inputs:
1. `snapshot_store` — the snapshot store, passed in (it is already standalone). (`settings_store` is not an input: it is used once, for `last_read_error` in `_report_discarded_settings`, which is a report about the settings file, not data loading — it stays in the shell, and `_report_discarded_settings` stays app-side, called from where the restore is sequenced.)
2. `cache_var`, `stats_var` — the path variables, read.
3. `status` — the status StringVar, for the progress and status reporting the engine already does.
4. `progress` — the progress-bar widget.
5. `load_button` — the Load button widget, disabled during a load and re-enabled after.
6. `set_sync_menu_state` — callable, enabling/disabling the File → Sync scores entry.
7. `on_library_changed` — the narrow callback, delivered with (rows, preserve_selection) when a load or a sync finishes, for the table/filter/Course Builder part only: reset the dropdowns via `filter.set_choices(rows)`, tell the Course Builder (`on_library_reloaded`), and set the table's rows. This replaces `on_loaded` (see Q2).
8. `on_scores_sync_failed`, `on_load_failed` — callbacks, delivered with the same payloads today's handlers receive, for the failure paths.
9. `on_nothing_loaded` — callback, delivered when `load_cached_data` finds no snapshot, so the app does the initial refresh (today `load_cached_data` calls `refresh_table()` directly when nothing is restored, and no listed callback covered that path).
10. `dialog` — the DataPathsDialog component itself (one input), for `open()`, `set_note()`, and `maybe_show_first_run()`. The loader talks to the dialog, not to separate callables. Construction order: the dialog is constructed first, with late-bound lambdas for its `load_callback` and `paths_match_loaded` (proposal 0005's precedent — the lambdas resolve to the loader once it exists), and the loader takes the dialog in its constructor — see the App side paragraph.
11. `save_settings` — callable.
12. `root` — for `after()` scheduling of the result polling.

The Loader component gets 19 of the cluster's 21 methods (`_set_sync_menu_state` stays in the app; `_format_refresh_time` moves to `library_data.py` in Step 2). The workers move unchanged (`_load_worker`, `_sync_scores_worker` already touch no widgets). The result queue, the polling, and the progress/phase reporting move with them. The generation counters, the in-flight flags, and the five snapshot-summary counters move too — they are the engine's own state (see §2). The loader owns the rows, `loaded_source_paths`, and `last_refreshed_at` — they are load results produced by the engine, written only by the handlers and read mostly by the loader — and the handlers' engine half moves into the loader with them (see Q2): `_loaded`'s progress stop, button re-enable, in-flight flag, menu state, status text, and counters, and `_scores_synced`'s merge and snapshot write. The app-side part of each handler (reset the dropdowns, tell the Course Builder, set the table's rows) is the `on_library_changed` callback. The engine never touches the table or the filter variables directly; everything the UI needs arrives through the callbacks in (7), (8), and (9). `export_csv` reads `loader.rows` (or `filter.library_rows()`).

**LibraryFilter** (`library_filter.py`). One sentence: the filter pipeline — it decides which rows pass, and tells the table when something changed. Its constructor inputs:
- `parent` — for the dropdown widgets.
- The five filter variables, shared objects: `search_var`, `diff_var`, `pack_var`, `type_var`, `scored_var`. The app builds the dropdowns that write them; the filter reads them.
- `search_entry` — the search box widget, for focus, clear, and the cursor nudge after a chart-filter change.
- The three dropdown widgets (`diff_filter`, `pack_filter`, `type_filter`) — so `_loaded`'s dropdown reset becomes `filter.set_choices(rows)`.
- `root` — for `after()` scheduling of the search debounce.
- `dpi_scale` — the display scale factor, for the dropdowns and the search box.

That is twelve inputs. Errata (Step 5, PR #167): the constructor takes ten inputs, not twelve — `parent` and `dpi_scale` are omitted as dead inputs, since the dropdowns and search box arrive already built. The filter holds the rows it filters (set via `set_rows(rows)`). It exposes `set_rows(rows)`, `filter_rows(ignore_metric=None)`, `search_hint()`, `batch()`, `apply_chart_filter`, `focus_search`, `clear_search`, and `subscribe(callback)` — the callback is invoked when something changed, so the table refreshes. The filter's `batch()` contract keeps the exit refresh: `_loaded` does not call `refresh_table` — it relies on the batch exit's unconditional refresh, even when no dropdown value changed — and the `_loaded` tests assert exactly one refresh, which must stay pinned. The filter does not touch the Treeview, the stores, or the status line.

Construction order: the filter is constructed first, then the Distribution Panel (which takes `filter.filter_rows` and `filter.apply_chart_filter`), then the table (which takes the filter, subscribes to its change notification, and takes `panel.show_rows`). That order is acyclic — it is the reason the filter splits out (§7, Q1).

**LibraryTable** (`library_table.py`). One sentence: the table — the Treeview, its columns and sorting, and selection. Its constructor inputs, counted as individual values (the precedent from proposal 0005, which counted eight):
- `parent` — the table frame, for the Treeview.
- `filter` — the LibraryFilter component, for `filter_rows` and the change notification the table subscribes to.
- `dpi_scale` — the display scale factor.
- `column_visibility`, `group_visibility` — shared objects; the View menu binds them, and the table mutates them in place (it never rebinds them).
- A saved-layout seed — the initial column order, widths, and sort keys, read from settings at build (one input).
- `count_label` — the label showing the row count.
- `save_settings` — callable, invoked when the sort, the columns, or the layout change.
- `show_rows` — a callable the table invokes with the visible rows after each refresh, so the Distribution Panel keeps receiving its push (today `refresh_table` calls `distribution_panel.show_rows` directly).

That is nine inputs. The table owns its sort and column state — `sort_keys`, `column_order`, and `column_widths` are not inputs, because `sort_by` rebinds `sort_keys` and `reset_column_layout` rebinds `column_order`, so a shared input would go stale in the app after a sort click or a reset (no test catches it today), and `column_widths` is read once, at build, to seed the tree. The table exposes a `layout_state()` accessor that `_save_settings` reads (it reads the actual widths back from `tree.column`), so the app never holds a stale copy. `default_column_widths` is a pure lookup from the column name, computed in `_build` (130/92/76/105/150), so the table computes it itself as a constant or a function of `HEADERS`. `tree_tint` is not an input: the table creates the Treeview, so it creates its tint helper itself. `root` is not an input: it is derivable from `parent.after`. The app pushes the full library rows after a load or a sync via a `set_rows(rows)` method on the table (the push precedent from the Distribution Panel's `show_rows`); that is a method call, not a constructor input. (The filter holds the rows it filters; the table receives the rows to display via `set_rows`.)

The table exposes `refresh_table()` (keeping its name — see Q4 — and its `preserve_selection` parameter — `_scores_synced` calls it with `preserve_selection=True`), `selected_rows()`, and `library_rows()` — the last two are today's `_selected_rows_for_course` and `_library_rows_for_course`, which the app passes to the Course Builder. The table does not touch the stores, the paths, or the status line (except through the count label, which it owns).

**App side after the move.** Deleted from `LibraryApp`: the 55 methods of the four clusters, the `_data_paths_*` and worker state attributes, and the filter/column/sort state declarations (those become the filter's and the table's state). `__init__` shrinks to creating the shell, the stores, and the components; `_build` shrinks to laying out the frames and constructing the components in order — the filter first, then the Distribution Panel (which takes `filter.filter_rows` and `filter.apply_chart_filter`), then the table (which takes the filter and `panel.show_rows`); the loader after the status widgets exist; and the dialog first, with late-bound lambdas for its `load_callback` and `paths_match_loaded`, before the loader takes the dialog in its constructor. The app gains the narrow `on_library_changed(rows, preserve_selection)` callback (reset the dropdowns via `filter.set_choices(rows)`, tell the Course Builder, set the table's rows) and the `on_nothing_loaded` callback (the initial refresh when no snapshot is restored), plus the failure callbacks. The shell gains `_set_sync_menu_state` (17 methods). The widget factories (`_button`, `_entry`, `_combo`) stay app-side and are passed to the components, as today. The README's architecture paragraphs gain a sentence per new component, next to the other three.

## 5. What Does Not Change

- Everything the user sees: the window layout, the table, the columns and their drag/reorder, the sort behaviour, the filter dropdowns and search box, the Data Paths dialog (its fields, buttons, and note lines), the load progress bar and its phases, the status messages (including the discarded-settings, moved-paths, and newer-Stats hints), the sync refusal messages, and the About dialog.
- Load and sync semantics exactly: the scan, the snapshot restore, the scores-only sync, the mid-sync mtime guard, the empty-scores and matched-nothing refusals, the generation/staleness checks, and the snapshot write under the lock. The workers move unchanged.
- The filter semantics: `_filter_rows` keeps its exact behaviour (pack, type, difficulty, scored, and search filters, including the unreadable-directive hint), the batching rule (one refresh per batched change), and the search debounce.
- The settings keys, the snapshot format (schema version 4), and their place in `_save_settings`. No new settings key, no file-format change.
- The three existing components (Course Builder, Advanced Search, Distribution Panel) and their contracts. The table's `show_rows` push to the panel keeps today's ordering (rows stored before the hidden check, per proposal 0005 §5). The filter's `batch()` keeps the exit refresh: `_loaded` relies on the batch exit's unconditional refresh, even when no dropdown value changed, and the `_loaded` tests assert exactly one refresh. No geometry memory is added for anything new, and no keyboard shortcut appears.
- The `.CRS` output, the CSV export, and the course-builder ambiguity check.

## 6. Test Plan (for the implementation PRs)

## 7. Open Questions for Reviewers

- **Q1. Should the filter pipeline be its own component, or stay inside the table?** Decided: split it out as its own component (Option A, four components), per Claude's recommendation, adopted by the owner. The filter's inputs form a disjoint group from the table's (the filter half: five variables, the search box, nine methods, 94 lines; the view half: columns, sort, drag, tint, row insertion, sixteen methods, 203 lines), and the seam is two queries and one notification. The filter already has several consumers beyond the table (the panel, `_loaded`'s dropdown reset, the menus and Escape, Advanced Search). The decisive point is the constructor cycle in the three-component design: the table needs the panel's `show_rows`, but the panel needs the table's `filter_rows` and `apply_chart_filter` — splitting makes the construction order acyclic (filter, then panel, then table). GLM (Revision 1) argued the other way — the filter has no independent existence, and splitting replaces a function call with a notification seam — but the cycle and the disjoint inputs carried the decision. The staging gains a PR between Steps 4 and 5 (Step 5 is the filter move, Step 6 the table).
- **Q2. Where do the loader's result handlers live?** Decided: the handlers' engine half moves into the loader, per Claude's recommendation, adopted by the owner. The rows, loaded paths, refresh stamp, and snapshot counters are written only by the handlers and read mostly by the loader — the counters have a single writer (`_loaded`) and a single reader (`_sync_scores_worker`), both loader-side — so the loader owns them and the handlers' engine half with them. The app supplies one narrow callback, `on_library_changed(rows, preserve_selection)`, for the table/filter/Course Builder part only. GLM (Revision 1) argued the middle ground — the loader owns the state, the handlers stay in the app as callbacks — but the single-writer/single-reader and the fact that `_loaded` is mostly loader work carried the decision. The handlers are small (118 lines combined) and the app keeps only the narrow callback.
- **Q3. Where do the new components' live tests live?** Recommended: the headless component tests go in new files (`tests/test_data_paths_dialog.py`, `tests/test_library_loader.py`, `tests/test_library_filter.py`, `tests/test_library_table.py` — covered by the ubuntu job, which runs the whole suite); the live tests stay in `tests/test_library_visualizer.py`, which the `windows-ui` job already runs. Claude notes the `windows-ui` job lists two files explicitly, so a one-time workflow edit to run the whole suite there would end the problem — that is the owner's call. The alternative — adding the new files to the `windows-ui` job — needs a workflow edit, which only the owner can make (the app bot has no Workflows permission). If the owner prefers the workflow edit, it is a one-line change per file and the live tests move with their components.
- **Q4. Is `refresh_table` renamed to `refresh` in the move, or does the move stay rename-free?** Decided: keep `refresh_table` through the move PRs (ChatGPT-6 and Claude, against GLM), and rename afterwards if wanted. A rename-free move is easier to verify by normalized diff (about 40 test mentions), and the rename can follow as a small cleanup once the component is established. GLM preferred the rename — the component's public surface is being defined in this proposal, and shipping a public API whose first method is named after the old class's internal vocabulary is a small permanent wart — but the normalized-diff argument carried the decision for the move PRs.
